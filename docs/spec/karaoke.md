# Spec: karaoke (model manager, `Separate`, `Align`, `Melody`, key change)

What a karaoke host needs from the engine and nothing of what karaoke is: stems of a track, word times for known lyrics, the notes sung, and a key change. Code: `core::api::karaoke` (wire), `core::jobs::{separate,align,melody}` (pure), `engine::karaoke` (manager, runtime, executors). [new]

## 1. What runs where

| Piece | Runs as | In the image | In the macOS and Windows bundles |
|---|---|---|---|
| ONNX runtime (`Separate`, `Melody`, `Align` with a CTC model) | `ort` with `load-dynamic`, cargo feature `karaoke` | CPU library at `ORT_DYLIB_PATH` | `karaoke/`: the official release (MIT): on macOS with CoreML compiled in, on Windows the CPU build, which the Windows ML runtime installed on the machine replaces when present (see below) |
| Speech recogniser (`Align` fallback) | `whisper-cli` (whisper.cpp, MIT) spawned as a tool, `WHISPER_CLI_PATH` | built from a pinned release with Vulkan and a CPU fallback, plus the Vulkan loader and Mesa's Intel and AMD drivers (software device removed) | built from the same release in `karaoke/` (Metal on macOS, CPU on Windows) |
| Key change | ffmpeg `rubberband` filter on `ffmpeg-pitch` (`FFMPEG_PITCH_PATH`), the main ffmpeg when it has the filter | an ffmpeg of the same release built with librubberband | `karaoke/ffmpeg-pitch`: FFmpeg built with librubberband linked statically (GPLv3, source offer in `karaoke/licenses/ffmpeg-pitch/SOURCE`) |
| Models | files under `<FLIKS_DATA_DIR>/models` (default `<cache root>/models`) | none shipped, `/data` volume | none shipped |

`hello.features` (additive): `models` always; `onnx`, `karaoke-separate`, `karaoke-melody` when the runtime loads; `onnx-<provider>` for each provider the loaded library has (`cuda`, `migraphx`, `openvino`, `coreml`, and on Windows `nvtensorrtrtx`, `amdgpu`, `qnn`, `vitisai`, `webgpu`, `directml`); `karaoke-align` when the recogniser is installed or the ONNX runtime loads, and `align-vulkan` when it will run on a real Vulkan device (Linux, see `Align` rule 9); `pitch-shift` when an ffmpeg has the filter. `windows-ml` when the engine runs the Windows ML runtime of the machine (Windows, see below). `GET /v1/models` answers the same as `runtime` (`onnx`, `onnxError`, `providers`, `whisper`, `rubberband`, and on Windows 11 22H2 and later `windowsMl`). The three job kinds are in `hello.jobFamilies` as audio kinds whatever the features say: a host checks the features before it queues one.

The image ships the CPU library only. A host that wants a GPU mounts the whole `lib/` directory of one ONNX Runtime release (`libonnxruntime.so` and its `libonnxruntime_providers_shared.so`, `libonnxruntime_providers_cuda.so` or `libonnxruntime_providers_migraphx.so` beside it: the provider libraries are found next to the main one) and points `ORT_DYLIB_PATH` at `libonnxruntime.so`.

- CUDA: the release's provider is built for one CUDA major (12 or 13). The container needs that major's `cudart`, `cufft`, `curand`, `cuBLAS` and cuDNN 9 on `LD_LIBRARY_PATH` (the NVIDIA container toolkit injects the driver only) and a driver recent enough for it. A GPU the build has no kernels for (`no kernel image`) fails at the first run: the warm-up below catches it and the session falls back.
- MIGraphX: Microsoft publishes no MIGraphX tarball; the host builds ONNX Runtime with `--use_migraphx` or extracts the ROCm wheel's. It needs ROCm and MIGraphX libraries of the build's ROCm version, `--device /dev/kfd --device /dev/dri` and the `video` and `render` groups.
- OpenVINO has no ONNX Runtime build of its own to download.
- The GPU is index 0 of the provider (`device_id`); pick another with `CUDA_VISIBLE_DEVICES` (CUDA) or `HIP_VISIBLE_DEVICES` (MIGraphX) in the engine's environment.

A GPU session is created and then run once on zeros of the production shape (`[2, 1, 512, 1024]` for Spleeter) before the job starts, outside the stall watchdog: the failures that only show in a run (missing kernels, out of memory, cuDNN errors, and MIGraphX, which compiles the graph in its first run because `num_splits` is symbolic) make the session fall back to the next provider, then to the CPU, so `provider` says what really ran. A `Separate` session tries the providers in `PROVIDERS` order (`cuda`, `migraphx`, `coreml`, then the Windows ones), skipping those its request's `providers` does not allow, and falls back to the CPU when one cannot be created or run: the result says which ran, `cpu` when either of the two networks is on the CPU. `Melody` always runs on the CPU (SwiftF0 is 10 ms a call; a GPU only adds a session to build). OpenVINO's GPU device computed Spleeter's `vocals.onnx` wrong on Linux (Intel compute-runtime, about 62 % of the elements off): it is listed, and a session uses it only when the request's `providers` names it, like every provider that has not passed `provider-check`; on Windows it is wrong too (OpenVINO of Windows ML on an Intel Iris Xe: 25 to 100 % of the elements of the three networks off by more than 0.001). CUDA runs with TF32 off (ONNX Runtime turns it on by default) so a GPU result stays at the CPU's precision; MIGraphX runs in fp32, and a host environment with `ORT_MIGRAPHX_FP16_ENABLE=1` would turn fp16 on, which the numeric check has not covered. MIGraphX keeps its compiled programs in `ORT_MIGRAPHX_MODEL_CACHE_PATH`, which the engine sets to `<models dir>/.migraphx` when unset (ONNX Runtime 1.23 and later; older ones ignore it and compile on every job). MIGraphX runs only the nodes it supports and ONNX Runtime gives the whole graph to the CPU when more than ten are unsupported, while the session still says `migraphx`: `provider-check` flags a provider that is not clearly faster than the CPU, and `ORT_MIGRAPHX_DUMP_MODEL_OPS=1` makes the library list the nodes it left out. CoreML is the macOS library's provider: on an M-series Mac it matches the CPU within 2 % of the output peak (Spleeter vocals 0.1 % of elements off by more than 0.01, accompaniment 0.8 %, SwiftF0 identical) and runs Spleeter about 7 % faster; `examples/provider-check.rs` repeats the comparison for any provider, on the production shape (one split) and on four splits. The desktop bundles keep the library, `whisper-cli` and `ffmpeg-pitch` with their licences in `karaoke/` next to the engine binary (release assets `fliks-engine-karaoke-<platform>.tar.gz` or `.zip`, sha256 beside, built by `tools/karaoke-pack/build.sh` from the pins in `pins.env`); `ORT_DYLIB_PATH`, `WHISPER_CLI_PATH` and `FFMPEG_PITCH_PATH` default to that directory when it holds the file, and still override it. macOS is arm64 only. The engine asks the library for ONNX Runtime API 23, so one older than 1.23 does not load: the outputs of a plugin provider sit in host-accessible device memory that only that API reads.

**Windows.** The pack holds the official ONNX Runtime CPU build (`onnxruntime.dll`, MIT, licence and notices in `licenses/onnxruntime/`) and nothing of Microsoft's proprietary runtime: the Windows ML runtime's licence makes a redistributor indemnify Microsoft and bind end users to terms that protect it, which an AGPL project cannot carry. Windows ML is used as the shared system component it is meant to be.

1. The Windows ML runtime is the framework package of the Windows App SDK (`Microsoft.WindowsAppRuntime.2`, else `.1.8`; `onnxruntime.dll`, `DirectML.dll` and `Microsoft.Windows.AI.MachineLearning.dll` in its directory). A user installs it with Microsoft's installer or `winget install Microsoft.WindowsAppRuntime.2`; Store apps bring it too. Windows 11 22H2 (build 22621) and later: at start the engine asks the operating system for it with the dynamic dependency API (`TryCreatePackageDependency` and `AddPackageDependency`, `kernel32.dll`, process lifetime: the OS does not service the package while the engine runs), then loads that directory's `onnxruntime.dll` instead of the pack's. Nothing is shipped for this: the bootstrapper DLL of the Windows App SDK is not used, the call is the operating system's. The package must be registered for the user the engine runs as; a service account that never signed in has none. When the runtime is absent, or `ORT_DYLIB_PATH` names a library, the pack's CPU library runs.
2. With the system runtime on Windows 11 24H2 (build 26100) and later, the engine opens the catalog (`WinMLEpCatalog*`, the C API of the runtime's `Microsoft.Windows.AI.MachineLearning.dll`) and registers every certified provider already on the machine with `RegisterExecutionProviderLibrary`; a session then builds on that provider's devices (`SessionOptionsAppendExecutionProvider_V2`). Windows downloads and installs the providers it certifies for the hardware (NVIDIA TensorRT RTX, AMD GPU and MIGraphX, Qualcomm QNN, AMD VitisAI, WebGPU, OpenVINO) when the first model download starts (`POST /v1/models/{id}/download`): the engine never goes to the network for them at startup, and one that appears later is seen after a restart.
3. With the system runtime on any supported Windows with a Direct3D 12 GPU: its `DmlExecutionProvider` (`directml`).
4. The CPU.

A session takes the first of these paths that gives a network, each only for a provider the request allows; the pack alone is the last path. `runtime.windowsMl` (Windows 11 22H2 and later only, absent elsewhere and when `ORT_DYLIB_PATH` is set) says where the engine stands: `active` (it runs the system runtime), `restart` (the runtime is installed now but this engine started without it: ONNX Runtime cannot be swapped in a running process), `missing` (not installed: a host shows how to install it). Presence is checked on every call, so a host that offers an install re-reads it. A provider is named by its ONNX Runtime name without `ExecutionProvider`, lowercased (`NvTensorRtRtxExecutionProvider` is `nvtensorrtrtx`), except `DmlExecutionProvider`, `directml`. OpenVINO is a provider like the others there (the catalog offers it on Intel hardware). A host lists a provider in the `providers` of a `Separate` only after `provider-check` on real hardware showed fp16-level differences. DirectML on an Intel Iris Xe (driver 32.0.101.7088, Windows build 26300, runtime 2.6.5) matches the CPU: Spleeter vocals and accompaniment within 6e-4 of values up to 40, SwiftF0 within 3e-5, no element over 0.001, and the networks run 1.5 times faster; a whole `Separate` of a 3 minute track takes as long as on the CPU (7.8 s against 7.3 s), the rest of the job being the bound. `FLIKS_ORT_THREADS` sets the threads of a run (default half the cores, 2 to 8).

## 2. Model manager (`engine::karaoke::models`)

1. The manifest is built in. An entry has `id`, `kind` (`separation`, `alignment`, `melody`), `name`, `version`, `licence` (`name`, `text`, `clear`), `default` (the model a job takes when its request names none: one per kind) and `files[]` (`name`, `url`, `sha256`, `sizeBytes`). Every URL names a revision of its repository, so a moved file fails its hash instead of changing what runs. An entry whose weights have an unsettled licence has `licence.clear: false`; none is listed today.
2. `GET /v1/models` lists the manifest with each model's `state` (`absent`, `downloading`, `installed`, `failed`), `downloadedBytes`, `verifying` (the `downloading` state is a verification, which `DELETE` does not cancel), `bytesPerSecond` (while `downloading`: the transfer rate, or the hashing rate of a verification) and `error`. A model also says its `languages` (alignment: two-letter codes, empty for every language), `engine` (alignment: `ctc` or `whisper`), `homepage` (its card), `sizeBytes` (the manifest's files), `diskBytes` (its directory on disk), `installedVersion` and `outdated`. The response adds `modelsDir`, `freeBytes` (the filesystem holding it, absent when unknown), `usedBytes` (the whole directory, caches included) and `orphans`: the directories that no manifest entry names and that hold a model file (`*.onnx`, `*.bin` or `.installed.json`; `name`, `sizeBytes`; a name starting with `.` is a cache or a staging directory and is never listed), so a models directory set to a data directory never offers media or backups for deletion. `modelsDir` is `<FLIKS_DATA_DIR>/models` when the host sets `FLIKS_DATA_DIR`, else `<cache root>/models`.
3. `POST /v1/models/{id}/download` starts the download (`202`, the model, also when this model's download already runs; `200` when it is installed and current; `404` for an unknown id; `409` while a verification of it runs). Files are fetched one after the other into the staging directory `<dir>/.<id>.new/<name>.part` through redirects (at most five; one from https to http is refused), hashed as they arrive and renamed once size and sha256 match (a file already staged with the right hash is kept, which resumes a failed download); a mismatch or any failure removes the part file and leaves the model `failed` with the reason. Once every file is staged and `.installed.json` is written (both fsynced, then the directories), the staging directory replaces `<dir>/<id>/`; a failing rename of the installed copy fails the download with its error. A resumed download reports no speed for the files it re-hashes. On an `outdated` model or one `failed` by a verification the same call is the update: the installed copy keeps running until the swap, and a failed update leaves it as it was (still `installed` and `outdated`, with `error`). A second start while one runs fetches nothing more (it answers `202`), and a task never writes into the entry of a later start of the same model. A transfer that moves no byte for 60 s fails.
4. `DELETE /v1/models/{id}` stops a download and removes the model's directory and its staging directory (`204`; `404` for an unknown id; `409` while a verification runs, which it does not cancel; `500` with the reason when a removal fails). `DELETE /v1/models/orphans/{name}` removes one directory of `orphans` (`204`; `404` for any other name, which makes it unable to reach a model or a cache; `500` with the reason when the removal fails).
5. `ModelChanged { model }` events (SSE) follow a download or a verification: at its start, at most once a second while it runs (with `downloadedBytes` and `bytesPerSecond`), and at its end, a delete included.
6. `POST /v1/models/{id}/verify` re-hashes the files of an installed model against the hashes its install recorded (`202`, the model `downloading` and `verifying` with `downloadedBytes` counting the hashed bytes, also when a verification of it already runs; `404` unknown; `409` when it is not installed or a download of it runs). A mismatch leaves the model `failed` with `<file> does not match its sha256 (<digest>)`, files untouched; a new `download` replaces them. The verdict is kept in `<id>/.verify-failed`, so the model stays `failed` across a restart; a job refuses it with `model_missing: <id> failed its verification` (an `Align` takes another CTC model or the recogniser), and a passing verification or a new install clears it.
7. After a verified install the directory holds `.installed.json`: the manifest `version` and each file's `name`, `sha256` and `size`; `installedVersion` reads it; an install without it (copied by hand, or made before the record existed) never reports `installedVersion` nor `outdated`. A model is `installed` when every file of that record (else of the manifest, for a copy without one) is on disk with its size (the hash was checked before the file was kept), and `outdated` (the flag, `state` stays `installed`) when the recorded version differs from the manifest's: a job still runs it and stamps the version on disk. A job picks its model at the start: the request's `model`, else the kind's default. An unknown id, a model of another kind or one not installed fails the job with `model_missing: <text>`.

An alignment entry also says whether it is a CTC network (`wav2vec2-ctc-fr`, `wav2vec2-ctc-en`, `omniasr-ctc-300m`: files `model.onnx` and `vocab.json`) and the two-letter codes of its `languages` (empty: every language). `default` stays one per kind: for alignment it is the speech recogniser, and a CTC entry is picked by language (`Align` rule 1).

Manifest today: `spleeter-2stems` (separation, default, MIT), `swiftf0` (melody, default, MIT), `whisper-small-q5_1` (alignment, default, MIT), and the CTC alignment models, all Apache-2.0, half-precision ONNX exports of `tools/ctc-export` hosted as the assets `<id>.model.onnx` and `<id>.vocab.json` of the release `models-ctc-v1` of this repository: `wav2vec2-ctc-fr` (French, `jonatasgrosman/wav2vec2-large-xlsr-53-french`), `wav2vec2-ctc-en` (English, `facebook/wav2vec2-large-960h-lv60-self`) and `omniasr-ctc-300m` (every other language, `facebook/omniASR-CTC-300M`).

8. A model dropped from the manifest stays in `RETIRED`: at start the engine removes its directory, so it is neither listed nor picked and a job naming it fails `model_missing: unknown model <id>`. Today: `whisper-base-q5_1` (its word times are unreliable on every backend, `Align` rule 9).

9. At start (`Manager::new`) the engine finishes a swap a crash interrupted: a `.<id>.old` goes back to `<id>` when that is missing, any other `.<id>.old` is removed, as is the `.<id>.new` of an id the manifest no longer has (the staging of a manifest id is kept: a resumed download reuses its files).

## 3. `Separate`

Request: `{ type: "Separate", info, model?, vocals?, instrumental?, guide?, guideVocalsGain?, bitrateKbps?, providers? }` on `media` = the source. At least one output path; every path absolute, without control characters, distinct; `guideVocalsGain` 0 to 1 (default 0.25); `bitrateKbps` 16 to 512 (default 96); `providers` the hardware providers the networks may run on (`cpu` is always allowed; absent: every provider the runtime lists but `openvino`, the one known to fail on Linux; empty: the CPU only). `info` must be an audio file (job families).

1. The model is Spleeter's 2-stem U-Net (`vocals.onnx`, `accompaniment.onnx`): a magnitude spectrogram `[2 channels, splits, 512 frames, 1024 bins]` in, a stem estimate of the same shape out. Input is 44.1 kHz stereo: the source's first audio stream decoded by ffmpeg (`-ac 2 -ar 44100`, f32) and streamed to the engine.
2. STFT: 4096 window (periodic Hann), hop 1024; `LEAD` = 3072 zeros in front so the first samples sit under the whole overlap. Chunks of 512 frames go through both networks one at a time, so memory does not grow with the track. The masks are the energy shares `(v^2 + e/2) / (v^2 + a^2 + e)`, `e = 1e-10`, so the two stems sum to the mix. The network sees bins below 1024 (about 11 kHz); above, the vocal mask is 0 and the instrumental mask 1, so the instrumental keeps the top of the mix. The stems are the masked spectra of the left and right channels through the inverse STFT and overlap-add, normalised by the window gain.
3. A stem is written as 16-bit PCM in the job's scratch directory as its chunk finishes; `guide` = instrumental + `guideVocalsGain` x vocals. One ffmpeg run then encodes every output to Opus (`libopus`, `-vbr on`, Ogg) at `bitrateKbps`.
4. Atomic outputs, like `Merge` (`docs/spec/jobs.md` section 10): each output gets an exclusive `.<name>.merge-<8 hex>.tmp` beside it first, journaled with its file identity in the job's scratch (a boot removes those a crash left); a name that is taken fails the job before anything runs; at the end every file is fsynced and hard-linked to its name without replacing; when one publish fails, the ones already published are taken back. The job never overwrites a file, so the host names fresh paths.
5. Result `{ type: "Separate", separate: { model, modelVersion, provider, vocals?, instrumental?, guide?, durationSeconds } }`, each file `{ path, bytes }` with the request's path. `provider` is what ran the network: a provider name of section 1 or `cpu`. Progress follows the decoded seconds (0 to 95), then the encode.
6. Stalls are watched, there is no overall timeout: a long track on a slow CPU takes as long as it takes. A cancel stops the decoder and the worker thread between chunks and removes the temporary files.

## 4. `Align`

Request: `{ type: "Align", lines: [{ text, startMs?, endMs? }], language?, model?, providers? }` on `media` = the vocal stem (or any audio holding the singing). At most 3000 lines and 6000 words; a line's `endMs` is not before its `startMs`; `language` is a lowercase ISO 639 code of two or three letters (absent: detected); `providers` as in `Separate` except that absent means the CPU only.

1. Model. The language is the request's, else the one the lyrics are written in when the detector (`whatlang`) finds it reliably, else none; three-letter codes of English, French, German, Spanish, Italian, Dutch and Portuguese count as their two-letter ones. The model is the request's `model`, else the first installed CTC model of the manifest whose `languages` hold the language (or are empty), else the default recogniser's. So French and English use their own wav2vec2 model when it is installed, every other language (and one the lyrics do not reveal) Omnilingual, and the recogniser serves when no CTC model is installed. A CTC run that fails (no ONNX runtime, a broken model, an export whose vocabulary has a token the network lacks, a network run that fails on the CPU too, a table over 400 million cells) is repeated with the recogniser when it is installed, and the result's `fallback` holds the CTC reason; with no recogniser the job fails with it. A source that cannot be decoded or holds no audio (`corrupt: no audio decoded`), a cancel and a stall end the job and are never repeated.
2. CTC. The stem is decoded to 16 kHz mono f32 like `Melody`. The network takes `input_values [1, n]` (the audio, zero mean and unit variance per call when the export's `vocab.json` says `doNormalize`) and answers `logits [1, T, V]`, one frame per 20 ms, at least 3200 samples a call (shorter input is zero-padded). `vocab.json` holds `sampleRate`, `frameMs`, `doNormalize`, `blank`, `delimiter` and `vocab` (id to token; the tokens of one character are the alphabet; the lyrics are folded to the case the manifest entry declares: lower for `wav2vec2-ctc-fr` and `omniasr-ctc-300m`, whose vocabulary also holds capitals the model rarely emits, upper for `wav2vec2-ctc-en`). An export that is not 16 kHz and 20 ms frames, or whose vocabulary has an id the network has no class for (checked on the answer of the warm-up run, or on one run of silence on the CPU, when the model is loaded, before the stem is decoded), fails the CTC run. A call covers at most 30 s with 1 s of audio around it, dropped from the answer (Omnilingual refuses 40 s), so a longer span goes through in chunks. The network runs once over the whole track and its logits become log-probabilities (`Emissions::from_logits`, a softmax over every class) of which only the blank, the classes of the lyrics' characters (`ctc::lyric_ids`) and the best non-blank class (what a character the vocabulary lacks scores) are kept, so a track's emissions stay a few MB whatever the number of classes. `ctc::align` (`core::jobs::ctc`) forces all the lyrics on them in one Viterbi pass:
   - States: a star before each line with a token and after the last, then each token followed by a blank, a delimiter between two words. A star scores the blank's log-probability, at least -2.3 per frame, so audio the lyrics do not explain costs no more than silence.
   - Bands: a line with times may only sit in its band, from 2 s before its start to 1.5 s after the next timed line's start (at most the line's length plus 3 s, inside the audio); a line without times, from the start to 1.5 s after the next timed line starts. The star before a line is active from the start of the previous line's band to the end of its own, so neighbouring lines share the frames they both reach. A band with fewer frames than its line's required tokens (one a token, a delimiter between words, a blank between equal tokens in a row) reaches the next band's end. A line whose band cannot follow the lines before it (a block pasted with stale times) is placed like a line without times, from where the previous words end; one that fits nowhere gets no tokens and is timed between its neighbours. A pass with no path at all is redone without any times.
   - Table: back pointers (two bits a cell) are kept only for the states between the lowest and the highest one whose band holds the frame, and a cell outside its band is never computed: a song's table is under 1 MB. Only a table of over 400 million cells (100 MB, an absurd input) is refused, with the reason `the lyrics and the audio are too long for one CTC pass`: the count depends on the lyrics and the length alone, so it is checked before the network runs. 10 minutes with 800 words and no times fit.
   - Voicing: the stem's RMS per 20 ms frame is compared with the loud level around it, the 95th percentile within 10 s (never under 25 dB below the track's own). A frame is silent when it is 35 dB or more under that level, or when it is 20 dB under it and within 6 dB of the track's noise floor (its 10th percentile: a stem with bleed has no digital silence), and in a run of at least 100 ms. A chunk of 30 s that is silent throughout is not run through the network, its frames are blank. The blanks between a word's tokens lose 3 per silent frame, so silence goes to the blanks between words or to the star instead of stretching a word (a token itself may sit on the frame before the sound: the network fires ahead of it). A word ends where its last token does, held over the frames after it while they are voiced and within 15 dB of the level of its tokens, up to the next word's start and for at most 4 s; a word followed by a word without tokens is not held, the gap is the other word's.
   - Optional spans: see rule 4.
3. Providers. The network runs on the CPU unless the request's `providers` names one: it then takes the first allowed provider that gives a session and survives a run on one second of zeros, else the CPU (`Separate`'s rules, section 1). A run on that provider that fails later, a stop aside (a real call is longer than the warm-up: memory, a graph compiled on first use) is repeated once from the start on the CPU, and the job takes the CPU's result (`backend` says `ctc-cpu`).
4. Lyric words are the whitespace-separated tokens of a line, with their UTF-8 byte ranges in the line's `text`. A line ending in `x2`, `(x2)`, `[x2]`, `2x` (also with `x` as `×`, up to 9) is sung that many times: it is expanded before the alignment, the marker is not a word, and a line with times shares them evenly between its copies. Words inside parentheses (one span per pair, `a (b c) d`) and every copy after the first of a repeated line are optional: the CTC search may jump over a span, from the blank before its first token to the blank after its last (a span opening its line also drops the delimiter after it), when the audio does not sing it, and the skipped words are timed like words without tokens. A word made only of a `[...]` label (`[Chorus]`, `[Verse 1]`) has no tokens and is never counted; the `[...]` parts of other words are not read. Adjacent spans can all be skipped.
5. Result `{ type: "Align", align: { model, modelVersion, backend, lines, matched, fallback? } }`. `backend` is `ctc-<provider>` (`ctc-cpu`, `ctc-cuda`...) for a CTC run, else what ran the recogniser: `vulkan`, `metal` or `cpu`; `model` is the model that placed the words; `fallback` (absent unless the recogniser stood in for a CTC model) is the reason the CTC run failed. `lines[]` has one entry per copy, in order: `{ line, repeat, startMs, endMs, matched, words: [{ text, byteStart, byteEnd, startMs, endMs }] }`; `line` is the request index, `repeat` the copy's ordinal. `matched` (0 to 1) is the share of lyric words found (CTC: whose mean log-probability reaches the threshold; recogniser: paired with a heard word): low means the timing is mostly interpolated. An optional word counts only when found, a label never, so a skipped translation or a repeat sung once costs nothing; the entry's `matched` is the same share over the copy's words: 1 when none is left to find (also a copy of optional words none of which was found), and what a result without the field reads as. An audio with no words still answers (`matched` 0, the words spread inside the line times, or one after another from 0).
6. Failure modes: no CTC model and no recogniser installed is `model_missing`, a recogniser tool that is not there `unsupported`, a recogniser that exits non-zero fails the job with its stderr tail, after a run on a GPU was repeated on the CPU (rule 9).

The speech recogniser path (the fallback), rules 7 to 9:

7. The stem is decoded to 16 kHz mono WAV in the scratch directory; `whisper-cli -m <model> -f <wav> -l <language|auto> -ml 1 -sow -oj -of <prefix> -np -t <threads> [-ng] --prompt <first 400 characters of the lyrics>` gives one word per JSON entry with millisecond offsets (`-l` is the request's language only). The prompt makes the recogniser hear the known words. Bracketed or parenthesised entries (`[MUSIC]`) and empty ones are not words.
8. Matching is an order-preserving pairing of lyric words with heard words, best total similarity (a word is compared lowercased with only letters and digits kept: equal scores 3, a misreading within a quarter of the length, for words of four or more letters, scores 1). A lyric word of a line with times only pairs with a heard word within 1.5 s of the line. A paired word takes the heard word's times. A run of unpaired words shares the time between its neighbours by length (70 ms a character, 120 ms at least), inside the line's times when it has them; a heard word that outlasts the next is cut at its start. The result never runs backwards.
9. On Linux the recogniser runs on a Vulkan device when one is usable, else on the CPU (`-ng`). Usable means the Vulkan loader (`libvulkan.so.1`) creates an instance and lists a device that is not a software one (type `cpu`, Mesa's llvmpipe): the image removes llvmpipe's ICD so a software device is never picked, and the engine ignores one a host adds. The probe runs once, with the tools. `backend` of the result says what ran (`cpu` after a fallback too) and `align-vulkan` is in `hello.features` when the probe found a device. A run on the GPU that fails (driver, out of memory, a device lost) is repeated once on the CPU with `-ng` and the job fails only if that fails too; a cancel or a stall is never repeated. The shader compile of a first run costs about 24 s on Mesa ANV (`small`: 4 s once `base` had filled the cache): the engine sets `MESA_SHADER_CACHE_DIR` to `<models dir>/.shader-cache` when unset, so a models volume keeps it. A container needs `--device /dev/dri` (and the `render` group) for Intel and AMD; NVIDIA's Vulkan ICD comes with the container toolkit (`NVIDIA_DRIVER_CAPABILITIES=compute,utility,graphics`).

   Ground truth (`tools/align-check`: 21 generated speech clips of 24 to 43 s, English and French, clean, over music and fast, word times known to the millisecond, the engine's own `Align`, whisper.cpp v1.9.5, Arc A370M and the Raptor Lake iGPU through Mesa ANV, 336 runs, deterministic). `small` on Vulkan is equivalent to the CPU and marginally better: on every clip it lies inside or below the CPU's own range (flash attention on and off), mean error 284 ms against 291 and 292 ms, within 500 ms for 85 % of the words against 83 % and 84 %, about 2.4x faster (5 s against 12 s for a clip once the shaders are cached). Both GPUs give identical times. The gap that an earlier comparison against the CPU on one 45 s clip showed (64 of 81 words equal in position) is decoding sensitivity (the CPU's own times move with flash attention), not a backend error. `base` is unreliable on every backend (a clip moves by seconds between flash attention on and off, `fr-espeakF2` is 6 to 9 s off everywhere), so it is not in the manifest. Not measured: real singing over a separated stem, NVIDIA and AMD. The Vulkan build and its runtime add about 0.3 GB to the image.

## 5. `Melody`

Request: `{ type: "Melody", spans: [{ startMs, endMs }], model? }` on `media` = the vocal stem. A span ends after it starts; at most 100000 spans.

1. The stem is decoded to 16 kHz mono f32 and run through SwiftF0 (`audio [1, n]`, `fmin` 46.875, `fmax` 2093.75, out `pitch` and `confidence` per 256-sample frame, 16 ms) in windows of 1875 frames with 11 frames of left context and 10 of look-ahead, so each frame is what one pass over the file gives. A frame whose 256 samples peak under 0.001 has confidence 0 (the network answers digital silence at random). A frame is voiced from confidence 0.25 (sung frames of a separated stem often score 0.2 to 0.4).
2. Voiced frames become MIDI pitch (`69 + 12 log2(f / 440)`). A frame more than 15 semitones from the median of the voiced frames inside the spans within 250 frames (4 s) of it (the singer's register, the whole track's when none is near) is dropped, unless it lies within 0.5 semitone of the median of the in-register voiced frames within eight frames of it once divided by a harmonic number from 2 to 8 (the network reporting a harmonic of the sung pitch), in which case it is moved there: otherwise it is a harmonic or another instrument left in the stem. A frame that lands within 2 semitones of the median of the voiced frames within 40 frames (640 ms) once moved by whole octaves is moved there (an octave error) when its run (voiced frames moved by the same octave, gaps of up to eight frames bridged) has at most 12 voiced frames (192 ms) and the step into it from the voiced frame before, and the step out to the one after (when within eight frames), are each a whole octave within 0.75 semitone: a longer run, or one entered by another interval, is a sung note and stays. The result is smoothed by a median over five frames. Per span, a note ends when the pitch stays more than 1 semitone from the note's median for four frames, or the voice stops for more than eight frames (128 ms; shorter gaps, a consonant, are bridged). A note under six voiced frames (96 ms) lengthens the previous note (its end moves to the fragment's end) when it starts within eight frames of that note's end, else the next one (its start moves) when within eight frames of its start, else it is dropped; a note's `midi` stays the median of its own frames. Then two notes within 0.75 semitone of each other with at most ten frames (160 ms) between them become one. A note is `{ startMs, endMs, midi }` within the span, `midi` the median of its frames (fractional, two decimals).
3. Result `{ type: "Melody", melody: { model, modelVersion, spans } }`: `spans[i]` is the notes of request span `i`; an unvoiced span has none.

## 6. Key change

`DecideSelection.pitchSemitones` (item sessions, `media.parts` as for any item; clamped to +-12; absent or 0: none) makes the item a Transcode (reason `PitchShifted`) whatever the client could play or copy, and adds `rubberband=pitch=2^(n/12):pitchq=quality` to the audio filter chain of every run, after the alignment and downmix, before the padding. The session's cache directory has its own hash for a non-zero shift (a zero shift keeps the hash it always had), so each key has its own cache. Runs are spawned through the ffmpeg that has the filter (`hello.features` `pitch-shift`); with none, the segment request fails and the run never starts. That ffmpeg is not the one with libfdk, so a shifted AAC item is always encoded with the native encoder. The key of a running session does not change: the host opens another session.

## 7. Errors of jobs

A job that cannot start for want of something the host can fix ends `failed` with `error` = `<code>: <text>`: `model_missing` (unknown id, wrong kind, not installed; the text names the download route) or `unsupported` (no ONNX runtime in this build or host, no recogniser). Those fail before any file is written. Other failures follow `docs/spec/jobs.md`; a source with no decodable audio is `corrupt: no audio decoded`.
