# Spec: karaoke (model manager, `Separate`, `Align`, `Melody`, key change)

What a karaoke host needs from the engine and nothing of what karaoke is: stems of a track, word times for known lyrics, the notes sung, and a key change. Code: `core::api::karaoke` (wire), `core::jobs::{separate,align,melody}` (pure), `engine::karaoke` (manager, runtime, executors). [new]

## 1. What runs where

| Piece | Runs as | In the image | In the macOS and Windows bundles |
|---|---|---|---|
| ONNX runtime (`Separate`, `Melody`) | `ort` with `load-dynamic`, cargo feature `karaoke` | CPU library at `ORT_DYLIB_PATH` | `karaoke/`: the official release on macOS (CoreML compiled in); on Windows the Windows ML runtime (ONNX Runtime 1.28 with DirectML, see below) |
| Speech recogniser (`Align`) | `whisper-cli` (whisper.cpp, MIT) spawned as a tool, `WHISPER_CLI_PATH` | built from a pinned release | built from the same release in `karaoke/` (Metal on macOS, CPU on Windows) |
| Key change | ffmpeg `rubberband` filter on `ffmpeg-pitch` (`FFMPEG_PITCH_PATH`), the main ffmpeg when it has the filter | an ffmpeg of the same release built with librubberband | `karaoke/ffmpeg-pitch`: FFmpeg built with librubberband linked statically (GPLv3, source offer in `karaoke/licenses/ffmpeg-pitch/SOURCE`) |
| Models | files under `FLIKS_MODELS_DIR` (default `<cache root>/models`) | none shipped, `/models` volume | none shipped |

`hello.features` (additive): `models` always; `onnx`, `karaoke-separate`, `karaoke-melody` when the runtime loads; `onnx-<provider>` for each provider the loaded library has (`cuda`, `migraphx`, `openvino`, `coreml`, and on Windows `nvtensorrtrtx`, `amdgpu`, `qnn`, `vitisai`, `webgpu`, `directml`); `karaoke-align` when the recogniser is installed; `pitch-shift` when an ffmpeg has the filter. `GET /v1/models` answers the same as `runtime` (`onnx`, `onnxError`, `providers`, `whisper`, `rubberband`). The three job kinds are in `hello.jobFamilies` as audio kinds whatever the features say: a host checks the features before it queues one.

The image ships the CPU library only. A host that wants a GPU mounts the whole `lib/` directory of one ONNX Runtime release (`libonnxruntime.so` and its `libonnxruntime_providers_shared.so`, `libonnxruntime_providers_cuda.so` or `libonnxruntime_providers_migraphx.so` beside it: the provider libraries are found next to the main one) and points `ORT_DYLIB_PATH` at `libonnxruntime.so`.

- CUDA: the release's provider is built for one CUDA major (12 or 13). The container needs that major's `cudart`, `cufft`, `curand`, `cuBLAS` and cuDNN 9 on `LD_LIBRARY_PATH` (the NVIDIA container toolkit injects the driver only) and a driver recent enough for it. A GPU the build has no kernels for (`no kernel image`) fails at the first run: the warm-up below catches it and the session falls back.
- MIGraphX: Microsoft publishes no MIGraphX tarball; the host builds ONNX Runtime with `--use_migraphx` or extracts the ROCm wheel's. It needs ROCm and MIGraphX libraries of the build's ROCm version, `--device /dev/kfd --device /dev/dri` and the `video` and `render` groups.
- OpenVINO has no ONNX Runtime build of its own to download.
- The GPU is index 0 of the provider (`device_id`); pick another with `CUDA_VISIBLE_DEVICES` (CUDA) or `HIP_VISIBLE_DEVICES` (MIGraphX) in the engine's environment.

A GPU session is created and then run once on zeros of the production shape (`[2, 1, 512, 1024]` for Spleeter) before the job starts, outside the stall watchdog: the failures that only show in a run (missing kernels, out of memory, cuDNN errors, and MIGraphX, which compiles the graph in its first run because `num_splits` is symbolic) make the session fall back to the next provider, then to the CPU, so `provider` says what really ran. A `Separate` session tries the providers in `PROVIDERS` order (`cuda`, `migraphx`, `coreml`, then the Windows ones), skipping those its request's `providers` does not allow, and falls back to the CPU when one cannot be created or run: the result says which ran, `cpu` when either of the two networks is on the CPU. `Melody` always runs on the CPU (SwiftF0 is 10 ms a call; a GPU only adds a session to build). OpenVINO's GPU device computed Spleeter's `vocals.onnx` wrong on Linux (Intel compute-runtime, about 62 % of the elements off): it is listed, and a session uses it only when the request's `providers` names it, like every provider that has not passed `provider-check`; whether the Windows Intel driver does better is for `provider-check` to say. CUDA runs with TF32 off (ONNX Runtime turns it on by default) so a GPU result stays at the CPU's precision; MIGraphX runs in fp32, and a host environment with `ORT_MIGRAPHX_FP16_ENABLE=1` would turn fp16 on, which the numeric check has not covered. MIGraphX keeps its compiled programs in `ORT_MIGRAPHX_MODEL_CACHE_PATH`, which the engine sets to `<models dir>/.migraphx` when unset (ONNX Runtime 1.23 and later; older ones ignore it and compile on every job). MIGraphX runs only the nodes it supports and ONNX Runtime gives the whole graph to the CPU when more than ten are unsupported, while the session still says `migraphx`: `provider-check` flags a provider that is not clearly faster than the CPU, and `ORT_MIGRAPHX_DUMP_MODEL_OPS=1` makes the library list the nodes it left out. CoreML is the macOS library's provider: on an M-series Mac it matches the CPU within 2 % of the output peak (Spleeter vocals 0.1 % of elements off by more than 0.01, accompaniment 0.8 %, SwiftF0 identical) and runs Spleeter about 7 % faster; `examples/provider-check.rs` repeats the comparison for any provider, on the production shape (one split) and on four splits. The desktop bundles keep the library, `whisper-cli` and `ffmpeg-pitch` with their licences in `karaoke/` next to the engine binary (release assets `fliks-engine-karaoke-<platform>.tar.gz` or `.zip`, sha256 beside, built by `tools/karaoke-pack/build.sh` from the pins in `pins.env`); `ORT_DYLIB_PATH`, `WHISPER_CLI_PATH` and `FFMPEG_PITCH_PATH` default to that directory when it holds the file, and still override it. macOS is arm64 only.

**Windows.** The pack holds the Windows ML runtime, the self-contained, unpackaged deployment of the `Microsoft.Windows.AI.MachineLearning` NuGet package (2.5.96, Windows 10 19H1 and later, x64): `onnxruntime.dll` (1.28, the DirectML provider built in), `DirectML.dll` and `Microsoft.Windows.AI.MachineLearning.dll`, with Microsoft's licence and notices in `licenses/windows-ml/`. Nothing needs the Windows App SDK runtime or a package identity. A session takes the first of three paths that gives a network, each only for a provider the request allows:

1. Windows 11 24H2 (build 26100) and later: the engine opens the catalog (`WinMLEpCatalog*`, the C API of `Microsoft.Windows.AI.MachineLearning.dll`) and registers every certified provider already on the machine with `RegisterExecutionProviderLibrary`; a session then builds on that provider's devices (`SessionOptionsAppendExecutionProvider_V2`). Windows downloads and installs the providers it certifies for the hardware (NVIDIA TensorRT RTX, AMD GPU and MIGraphX, Qualcomm QNN, AMD VitisAI, WebGPU, OpenVINO) when the first model download starts (`POST /v1/models/{id}/download`): the engine never goes to the network for them at startup, and a provider that appears later is seen by the next `hello`.
2. Any Windows with a Direct3D 12 GPU: the bundled runtime's `DmlExecutionProvider` (`directml`).
3. The CPU.

Before Windows 11 24H2 the catalog is not opened and nothing is logged above debug. A provider is named by its ONNX Runtime name without `ExecutionProvider`, lowercased (`NvTensorRtRtxExecutionProvider` is `nvtensorrtrtx`), except `DmlExecutionProvider`, `directml`. OpenVINO is a provider like the others there (the catalog offers it on Intel hardware). No Windows provider has been compared with the CPU by this repository's CI (its runners have no GPU): a host lists a provider in the `providers` of a `Separate` only after `provider-check` on real hardware showed fp16-level differences. `FLIKS_ORT_THREADS` sets the threads of a run (default half the cores, 2 to 8).

## 2. Model manager (`engine::karaoke::models`)

1. The manifest is built in. An entry has `id`, `kind` (`separation`, `alignment`, `melody`), `name`, `version`, `licence` (`name`, `text`, `clear`), `default` (the model a job takes when its request names none: one per kind) and `files[]` (`name`, `url`, `sha256`, `sizeBytes`). Every URL names a revision of its repository, so a moved file fails its hash instead of changing what runs. An entry whose weights have an unsettled licence has `licence.clear: false`; none is listed today.
2. `GET /v1/models` lists the manifest with each model's `state` (`absent`, `downloading`, `installed`, `failed`), `downloadedBytes` and `error`.
3. `POST /v1/models/{id}/download` starts the download (`202`, the model; `200` when it is installed already or running; `404` for an unknown id). Files are fetched one after the other into `<dir>/<id>/<name>.part` through redirects (at most five; one from https to http is refused), hashed as they arrive and renamed once size and sha256 match; a mismatch or any failure removes the part file and leaves the model `failed` with the reason. A second start while one runs fetches nothing more, and a task never writes into the entry of a later start of the same model. A transfer that moves no byte for 60 s fails.
4. `DELETE /v1/models/{id}` stops a download and removes the model's directory (`204`; `404` for an unknown id).
5. `ModelChanged { model }` events (SSE) follow a download: at its start, at most once a second while it runs, and at its end, a delete included.
6. A model is `installed` when every file is on disk with its manifest size (the hash was checked before the file was kept). A job picks its model at the start: the request's `model`, else the kind's default. An unknown id, a model of another kind or one not installed fails the job with `model_missing: <text>`.

Manifest today: `spleeter-2stems` (separation, default, MIT), `swiftf0` (melody, default, MIT), `whisper-small-q5_1` (alignment, default, MIT) and `whisper-base-q5_1` (alignment, MIT, faster and less exact).

## 3. `Separate`

Request: `{ type: "Separate", info, model?, vocals?, instrumental?, guide?, guideVocalsGain?, bitrateKbps?, providers? }` on `media` = the source. At least one output path; every path absolute, without control characters, distinct; `guideVocalsGain` 0 to 1 (default 0.25); `bitrateKbps` 16 to 512 (default 96); `providers` the hardware providers the networks may run on (`cpu` is always allowed; absent: every provider the runtime lists but `openvino`, the one known to fail on Linux; empty: the CPU only). `info` must be an audio file (job families).

1. The model is Spleeter's 2-stem U-Net (`vocals.onnx`, `accompaniment.onnx`): a magnitude spectrogram `[2 channels, splits, 512 frames, 1024 bins]` in, a stem estimate of the same shape out. Input is 44.1 kHz stereo: the source's first audio stream decoded by ffmpeg (`-ac 2 -ar 44100`, f32) and streamed to the engine.
2. STFT: 4096 window (periodic Hann), hop 1024; `LEAD` = 3072 zeros in front so the first samples sit under the whole overlap. Chunks of 512 frames go through both networks one at a time, so memory does not grow with the track. The masks are the energy shares `(v^2 + e/2) / (v^2 + a^2 + e)`, `e = 1e-10`, so the two stems sum to the mix. The network sees bins below 1024 (about 11 kHz); above, the vocal mask is 0 and the instrumental mask 1, so the instrumental keeps the top of the mix. The stems are the masked spectra of the left and right channels through the inverse STFT and overlap-add, normalised by the window gain.
3. A stem is written as 16-bit PCM in the job's scratch directory as its chunk finishes; `guide` = instrumental + `guideVocalsGain` x vocals. One ffmpeg run then encodes every output to Opus (`libopus`, `-vbr on`, Ogg) at `bitrateKbps`.
4. Atomic outputs, like `Merge` (`docs/spec/jobs.md` section 10): each output gets an exclusive `.<name>.merge-<8 hex>.tmp` beside it first, journaled with its file identity in the job's scratch (a boot removes those a crash left); a name that is taken fails the job before anything runs; at the end every file is fsynced and hard-linked to its name without replacing; when one publish fails, the ones already published are taken back. The job never overwrites a file, so the host names fresh paths.
5. Result `{ type: "Separate", separate: { model, modelVersion, provider, vocals?, instrumental?, guide?, durationSeconds } }`, each file `{ path, bytes }` with the request's path. `provider` is what ran the network: a provider name of section 1 or `cpu`. Progress follows the decoded seconds (0 to 95), then the encode.
6. Stalls are watched, there is no overall timeout: a long track on a slow CPU takes as long as it takes. A cancel stops the decoder and the worker thread between chunks and removes the temporary files.

## 4. `Align`

Request: `{ type: "Align", lines: [{ text, startMs?, endMs? }], language?, model? }` on `media` = the vocal stem (or any audio holding the singing). At most 3000 lines and 6000 words; a line's `endMs` is not before its `startMs`; `language` is a lowercase ISO 639 code of two or three letters (absent: detected).

1. The stem is decoded to 16 kHz mono WAV in the scratch directory; `whisper-cli -m <model> -f <wav> -l <language|auto> -ml 1 -sow -oj -of <prefix> -np -t <threads> --prompt <first 400 characters of the lyrics>` gives one word per JSON entry with millisecond offsets. The prompt makes the recogniser hear the known words. Bracketed or parenthesised entries (`[MUSIC]`) and empty ones are not words.
2. Lyric words are the whitespace-separated tokens of a line, with their UTF-8 byte ranges in the line's `text`. A line ending in `x2`, `(x2)`, `[x2]`, `2x` (also with `x` as `×`, up to 9) is sung that many times: it is expanded before the matching, the marker is not a word, and a line with times shares them evenly between its copies.
3. Matching is an order-preserving pairing of lyric words with heard words, best total similarity (a word is compared lowercased with only letters and digits kept: equal scores 3, a misreading within a quarter of the length, for words of four or more letters, scores 1). A lyric word of a line with times only pairs with a heard word within 1.5 s of the line.
4. A paired word takes the heard word's times. A run of unpaired words shares the time between its neighbours by length (70 ms a character, 120 ms at least), inside the line's times when it has them; a heard word that outlasts the next is cut at its start. The result never runs backwards.
5. Result `{ type: "Align", align: { model, modelVersion, lines, matched } }`. `lines[]` has one entry per copy, in order: `{ line, repeat, startMs, endMs, words: [{ text, byteStart, byteEnd, startMs, endMs }] }`; `line` is the request index, `repeat` the copy's ordinal. `matched` (0 to 1) is the share of lyric words found in what was heard: low means the timing is mostly interpolated. An audio with no words still answers (`matched` 0, the words spread inside the line times, or one after another from 0).
6. Failure modes: no recogniser installed is `unsupported`, a model not installed is `model_missing`, a recogniser that exits non-zero fails the job with its stderr tail.
7. The recogniser always runs on the CPU. whisper.cpp v1.9.5 built with Vulkan (Mesa ANV, Intel iGPU and Arc A370M) is 1.4x (base) to 1.9x (small) faster once its shaders are cached, but its word times are not the CPU's: on the same 45 s speech clip, with the lyrics prompt, 81 of 87 (base) and 64 of 81 (small) words match the CPU's in position, the median time difference is 10 ms (base) and 240 ms (small), the worst over 3 s, and the word counts differ. Both GPUs agree with each other and the flash attention switch moves the CPU's own times, so the gap is decoding sensitivity, not a bug to fix. Like OpenVINO, Vulkan is not shipped: the image would grow by about 0.25 GB for a result that does not match.

## 5. `Melody`

Request: `{ type: "Melody", spans: [{ startMs, endMs }], model? }` on `media` = the vocal stem. A span ends after it starts; at most 100000 spans.

1. The stem is decoded to 16 kHz mono f32 and run through SwiftF0 (`audio [1, n]`, `fmin` 46.875, `fmax` 2093.75, out `pitch` and `confidence` per 256-sample frame, 16 ms) in windows of 1875 frames with 11 frames of left context and 10 of look-ahead, so each frame is what one pass over the file gives. A frame whose 256 samples peak under 0.001 has confidence 0 (the network answers digital silence at random). A frame is voiced from confidence 0.5.
2. Per span, the voiced frames in it become MIDI pitch (`69 + 12 log2(f / 440)`), smoothed by a median over three frames. A note ends when the pitch stays more than 0.8 semitone from the note's median for three frames, or the voice stops for more than five frames (80 ms; shorter gaps, a consonant, are bridged). A note under three frames (48 ms) is dropped. A note is `{ startMs, endMs, midi }` within the span, `midi` the median of its frames (fractional, two decimals).
3. Result `{ type: "Melody", melody: { model, modelVersion, spans } }`: `spans[i]` is the notes of request span `i`; an unvoiced span has none.

## 6. Key change

`DecideSelection.pitchSemitones` (item sessions, `media.parts` as for any item; clamped to +-12; absent or 0: none) makes the item a Transcode (reason `PitchShifted`) whatever the client could play or copy, and adds `rubberband=pitch=2^(n/12):pitchq=quality` to the audio filter chain of every run, after the alignment and downmix, before the padding. The session's cache directory has its own hash for a non-zero shift (a zero shift keeps the hash it always had), so each key has its own cache. Runs are spawned through the ffmpeg that has the filter (`hello.features` `pitch-shift`); with none, the segment request fails and the run never starts. That ffmpeg is not the one with libfdk, so a shifted AAC item is always encoded with the native encoder. The key of a running session does not change: the host opens another session.

## 7. Errors of jobs

A job that cannot start for want of something the host can fix ends `failed` with `error` = `<code>: <text>`: `model_missing` (unknown id, wrong kind, not installed; the text names the download route) or `unsupported` (no ONNX runtime in this build or host, no recogniser). Those fail before any file is written. Other failures follow `docs/spec/jobs.md`; a source with no decodable audio is `corrupt: no audio decoded`.
