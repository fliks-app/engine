# Spec: live TV (M6)

The runtime half of the host's live TV: one upstream connection per (channel, mode, container, bitrate) shared by its viewers, ffmpeg's sliding-window HLS (or a raw tee for direct play), failover across upstreams, the DVR window, idle teardown and the data plane. Catalog, EPG, sources, per-channel access and the capacity policy stay in the host. Tags are relative to `fliks/backend/src/modules/livetv/` (`svc` = `services/livetv-session.service.ts`, `ctl` = `controllers/livetv.controller.ts`, `cap` = `services/livetv-capacity.service.ts`). Pure rules: `core::live`; runtime: `engine::live`; argv: `core::args::live` (`args.md` section 12). Plan: sections 5 (Live TV), 14 (M6).

## 1. Open (`POST /v1/live`)

`OpenLiveRequest { channelId, upstreams: [{ url, priority?, headers?, probedContainer?, probedVideoCodec?, probedAudioCodec?, atCapacity? }], caps: { directPlay?, maxBitrateBps?, useTs? }, ownerId?, capacityToken, atCapacity?, tags? }`.

- 400: no config yet, no upstream, an upstream URL whose scheme is not `http`, `https`, `rtmp(s|t|e)`, `rtsp(s)`, `rtp`, `udp` or `srt` (ffmpeg would read `file:`, `concat:`, ... from the engine's disk) [new], a bad `ownerId`. 503 + `Retry-After: 1` until hardware detection ends.
- Upstreams are tried in `priority` order, stable: the host puts the healthy ones first within a priority (its `compareHealth`, `lastError`/`lastOkAt` are host data). `upstream` indexes in answers and events are positions in the request's list. [ts:svc:338-340]
- `maxBitrateBps` snaps to the first rung `>=` it of 1.5/3/6/10/20 Mb/s, else 20 Mb/s, before anything reads it. [ts:svc:216-223,335-337]
- Mode (`core::live::decide_mode`): `directPlay: true` = `direct`; a `maxBitrateBps` = `transcode`; else `livetv.fastZap` `true` = `transcode`, `false` = `remux`, absent = `transcode` on a hardware host, `remux` on the CPU. [ts:svc:695-704]
- Direct: upstream 0 is probed first; a manifest container (`hls`, `applehttp`, `dash` in ffprobe's comma list, case-insensitive) re-decides with `directPlay: false`. [ts:svc:349-357]
- Key `<channelId>:<mode>:<ts|fmp4>:<maxBitrateBps or 0>` on the requested mode: a running session of the key is joined (no new upstream, no capacity needed). Concurrent opens of one key share one attempt and its outcome. [ts:svc:389-436,706-711]
- A new session: `atCapacity: true` answers 409 `{ code: "live_at_capacity" }` (the host's `assertBelowLimit` result, checked only when an upstream must open, as the TS does) [ts:svc:448-453]. An upstream with `atCapacity: true` (the host's verdict for its source, taken at open) is dropped from the session's failover order, so no attempt ever reaches it; all of them set answers the same 409. Then (non-direct) upstream 0 is probed, a `remux` of anything but `h264` runs as `transcode` (the key keeps `remux`) [ts:svc:459-463], the directory `<root>/live/<key with [^a-z0-9-] as _>-<seq>` is made, and section 2 starts it. Every upstream failing ends it: `LiveReleased { reason: failed }`, then 503 `{ code: "live_unavailable" }` (the host names an expired account from its own data) [ts:svc:524-545]; a direct session whose upstreams all served a manifest re-opens as non-direct under the same hold, without a release [ts:svc:363-367,527].
- Answer `OpenLiveResponse { sessionId, playPath, mode, upstream, capacityToken, probe?, dvrWindowSeconds, segmentSeconds, qoePipeline }`: `sessionId` is a viewer id (random, per open); `playPath` = `/api/livetv/sessions/<sid>/index.m3u8`, `direct.ts` for direct (the host appends `?token=`); `mode` the effective one; `upstream` the feeding one of the open that created the session; `capacityToken` the session's, i.e. the request's when this open started an upstream, a running session's when it joined (the host frees its own at once then); `probe` = what is known of that upstream; `dvrWindowSeconds` = `timeshiftMinutes * 60` (0 direct). `qoePipeline` = the TS's `qoePipeline` (source codec = active, else probed; transcode output `h264` at the cap else 4 Mb/s; encoder of the detected backend). [ts:svc:371-386,625-653,788-804]
- Settings (`EngineConfig.livetv`, the host's `livetv_*`): `segmentSeconds` 2 and `timeshiftMinutes` 15 (both floored at 1), `probeSeconds` 3, `fastZap` absent, `channelIdleSeconds` 30. `livetv_slot_release_seconds` stays in the host (capacity). [ts:svc:465-474,1140-1145]

## 2. Start and failover (`core::live::Failover`)

- Probe (`ensureProbed`): skipped when the upstream's video codec is known (from the request or an earlier probe of this session); else `ffprobe -v error -analyzeduration 3000000 -probesize 5000000 -show_entries format=format_name:stream=codec_type,codec_name -of csv=p=0 -user_agent .. [-headers ..] url`, 15 s timeout, under a playback slot; failure leaves it unknown (remux then transcodes). Parsing: a line whose last comma field is `video`/`audio`/`subtitle`/`data`/`attachment` is a stream (first video, first audio), the first other line is the container. [ts:svc:170-193,727-773]
- Recover: until an attempt succeeds, skip upstreams with 2 failures (all at 2: the session ends), attempt `upstreams[index % n]`; a failed attempt counts one failure on it, `index += 1`, `restarts += 1`. A running session failing (exit, stall, upstream closed) counts the same then recovers in place. Golden vectors `fixtures/live/failover.json`. [ts:svc:820-858,1087-1102]
- Packaged attempt: probe; a `remux` whose upstream is not `h264`, or differs from the codec in the running init, becomes `transcode` (fresh run); else a run after the first appends when `index.m3u8` exists (`append_list+discont_start`). Argv `core::args::live` (hwAccel = detected backend for transcode, `none` for remux; `audioCodec` = the probed one; headers: `User-Agent` and `Referer` go to `-user_agent`/`-headers`, other headers append to `-headers`). Success = any `seg-*` entry in the directory within 20 s (polled every 300 ms); the run exiting first fails it. A remux success records the upstream's codec as the active one. [ts:svc:862-927,1001-1047] [ts:services/live-ffmpeg-args.ts:97-215]
- Direct attempt: `GET url`, `http` or `https` (rustls, the platform's root certificates, `SSL_CERT_FILE`/`SSL_CERT_DIR` replacing them), the upstream's headers on every hop, `User-Agent` defaulting to `VLC/3.0.20 LibVLC/3.0.20`, 5 redirects, 30 s to the headers. A content type containing `mpegurl`, `dash+xml`, `application/xml`, `text/xml`, `text/html`, `application/json` or `text/plain`, or a first chunk opening (after a UTF-8 BOM and leading whitespace, within 16 bytes) with `#EXTM3U`, `<?xml` or `<MPD`, is a manifest: not streamable. No byte within 4 s still counts as a stream. Chunks then go to every direct viewer. [ts:svc:929-999]
- Events per attempt: `LiveAttempt { capacityToken, upstream, upstreamUrl, upstreamPriority, error?, probe? }`, `error` absent = this upstream now feeds the session (the host's `lastOkAt`), present = it failed (`lastError`; for an upstream that had fed the session, the host's release grace starts). `error` = `exited (code=<n|null>): <last 300 chars of stderr>` for a running exit, `no new segment for 15 s` for a stall, `upstream closed` for a direct upstream ending, the HTTP error of a direct connect, else `no segment produced within the startup window`. [ts:svc:840-856,918-925,1097]
- Running: every 200 ms the directory is listed; a higher `seg-N` than seen refreshes `lastSegmentAt` (direct: every chunk). The run exiting fails at once; every 5 s, more than 15 s without a new segment is a stall. [ts:svc:1049-1076]
- Every packaged run holds a playback slot of the ffmpeg budget while it lives (never waits, `jobs.md` section 3); direct sessions run no ffmpeg. [new]

## 3. Viewers, idle and teardown

- A viewer is one open: owner, tags, `openedAtMs`, `lastSeenMs`. Every data-plane request of its sid refreshes `lastSeenMs`. [ts:svc:371-381,590-601]
- Each tick, a viewer silent past `lifetime.liveSessionTtlMs` and with no open `direct.ts` response leaves (`SessionEnded { reason: "expired" }`). [ts:svc:281-302]
- `DELETE /v1/sessions/{sid}` of a live sid: the viewer leaves (`SessionEnded { reason: stopped or ?reason= }`, 204, idempotent), its `direct.ts` responses close. `POST /v1/revoke` with an `ownerId` and no `mediaFileIds` also removes that owner's viewers (`revoked`, counted in `sessions`). [ts:svc:549-559]
- No viewer for `channelIdleSeconds` (a rejoin cancels it): teardown. Every upstream failed: teardown, its viewers end with `failed`. Teardown stops ffmpeg (awaited; section 1 of runtime.md) or the connection, closes direct responses, deletes the directory, emits `LiveReleased { capacityToken, reason: idle|failed|shutdown }` (the host frees the slot and starts its release grace; on `failed` it bumps the channel's failure count). [ts:svc:1104-1164,1140-1145]
- Boot deletes `<root>/live`; shutdown stops every session. [ts:svc:258-318]
- `GET /v1/live[?ownerId]`, `GET /v1/live/{sid}`: `LiveSnapshot { sessionId, channelId, ownerId?, tags, mode, capacityToken, upstream, upstreamUrl, upstreamPriority, openedAtMs, lastSeenMs, videoCodec?, audioCodec?, container: fmp4|mpegts, viewersOnUpstream, restarts }` per viewer (the host's activity rows); `capacityToken`, `mode` and the current upstream (`upstream`, `upstreamUrl`, `upstreamPriority`) let the host rebuild its holds and load counters after a restart. [ts:svc:563-587]
- No `SessionOpened` for live: its payload is a VOD snapshot and the open's answer already carries everything. [new]

## 4. Data plane (`/api/livetv/sessions/:sid/...`, `GET`/`HEAD`)

Gate: unknown sid first (no resolver call), then the resolver `{ mediaId: <sid>, credential, purpose: "live" }` (cached per `ttlS`; the host checks the channel is still playable for that user, its `assertStillPlayable`). A denial answers 403 and ends the viewer (`revoked`) only when it carries the viewer's `ownerId` (a denial without one, or for another user, leaves it); the resolver's `ownerId` differing from the viewer's is 403; host unreachable: the known session keeps serving. [ts:ctl:201-215,245-318]

- `index.m3u8`: unknown sid 404 `Live TV session not found`; no `index.m3u8` yet (or a direct session) 404 `Playlist not ready yet`; else ffmpeg's playlist with `?token=<encodeURIComponent(token)>` appended to every URI line and `EXT-X-MAP` URI when the request has a non-empty `?token=` (`core::live::with_token`), `Content-Type: application/vnd.apple.mpegurl`, `Cache-Control: no-store`. [ts:ctl:59-82,245-266]
- `:segment`: unknown or direct sid 404 `Live TV segment not found`; a name other than `init.mp4` or `seg-<5+ digits>.(m4s|ts)` 400 `Invalid segment name: <name>`; a missing file 404 `Live TV segment not found`; else the file, `video/mp2t` for `.ts`, `video/mp4` otherwise, `Accept-Ranges: bytes`, single ranges (206/416), `Cache-Control: public, max-age=0`. A media segment emits `SegmentServed { track: video, rung: "live", index, waitedMs: 0, cacheHit: true, cmcdRaw }`. [ts:ctl:45-47,292-318]
- `direct.ts`: unknown or non-direct sid 404 `Live TV session not found`; else the shared upstream from now on, `Content-Type` = the upstream's (default `video/mp2t`), `Cache-Control: no-store`; a viewer more than 256 chunks (~4 MiB) behind is dropped, never the upstream. [ts:ctl:268-290] [ts:svc:210-212,682-693,977-983]
- Errors are Nest's JSON `{ statusCode, message, error }`; every answer has `Access-Control-Allow-Origin: *`.
- Gateway: engine `GET`/`HEAD` `/api/livetv/sessions/:sid/:segment`; `DELETE sessions/:sid` and `PUT sessions/:sid/state` stay the host's.

## 5. Host contract (capacity)

Before an open the host reserves `capacityToken` on the source of the first upstream without `atCapacity` and sends each upstream's `assertBelowLimit` verdict as `atCapacity` (sources it already holds count as free). Known ceiling: the verdicts are taken at the open and a failover does not re-ask, so a failover onto a source that filled after the open can exceed its `maxStreams` by one stream; closing it would need a host callback before every attempt, adding latency to each failover. It frees the reservation on 409, on `LiveReleased` (also sent before a 503), or when the answer's `capacityToken` is another (joined). A held token moves to the source of the upstream its last ok `LiveAttempt` names; `LiveAttempt.error` on a fed upstream and `LiveReleased` start that source's release grace (`recordRelease`). The engine's probes run inside the token's hold. [ts:cap:1-75] [ts:svc:448-453,1097,1159]

## 6. Deviations

- Stricter gate: the TS serves segments to any signed-in user holding the sid; the engine asks the resolver (`purpose: live`) for every route and checks the owner.
- An upstream URL scheme allowlist; a direct upstream that ends before its first byte fails the attempt (the TS counts it a stream after 4 s and the stall watchdog catches it).
- Segment polling (200 ms listing) instead of `fs.watch`; ffmpeg stops with SIGTERM then SIGKILL (TS: SIGKILL).
- Express's `ETag`/`Last-Modified` on segments are not sent. A leaving viewer's `direct.ts` closes (the TS keeps teeing until the socket closes).
- A failover run whose directory still holds segments counts as started at once, as in the TS (`hasSegment` sees the old ones): the stall watchdog judges it.
- Not ported: QoE production timing (`recordProduction`), the activity registry, the channel failure counters (the host updates them on `LiveReleased { reason: failed }`), the per-stream DB writes (the host persists `LiveAttempt`).
